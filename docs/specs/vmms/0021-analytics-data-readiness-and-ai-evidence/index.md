# 0021. Analytics data readiness and evidence-backed AI

**Status**: Implementation complete; runtime acceptance pending
**Scope**: [Analytics, mobile synchronization, and release readiness](../../../scope/vmms/index.md#8-analytics-mobile-synchronization-and-release-readiness)

Decision history: [rationale.md](rationale.md). Verification plan: [verify.md](verify.md).

## Summary

Complete VMMS analytics runtime readiness and improve the trustworthiness of
AI-generated fleet insights. Validate the DuckDB reporting mart and pgvector
index against core VMMS sources, make data freshness and coverage visible,
and attach source metrics and limitations to AI insights. Analytics remains
a derived, read-only view rather than an operational source of truth.

- VMMS cross-cutting FR-27.11: generated time, source update time, data age,

- VMMS cross-cutting FR-27.12: data-mart migrations and validation.

## Behavior

### Runtime data readiness

- Run existing DuckDB migrations and validators against clean and populated
  analytics stores. Repeated migration and sync runs must be safe and must
  not silently lose valid data.
- Compare a fixed core-VMMS source snapshot with the derived mart for vehicle
  and schedule counts, every schedule status, and report aggregates. Vehicle,
  schedule, and status parity is exact; maintenance-cost totals may differ by
  less than 0.01 due to numeric representation.
- Require 100% embedding coverage for eligible records: every non-deleted
  schedule and each checklist template with non-empty type/item content,
  matching current migration behavior.
- Run three fixed synthetic 1536-dimensional pgvector ranking queries; each
  expected fixture record must appear in the top three. This validates the
  vector ranking operator, not natural-language relevance over live records.
  User-facing semantic retrieval is outside this slice; current schedule
  search remains text-based.
- Do not publish a partial or failed refresh as a current, validated
  snapshot.

### Data health and freshness

- Show Admin and Operations a concise Analytics data-health state: current,
  stale, or unavailable; generated time; source update time; and data age.
- Reuse existing source metadata and the configured stale threshold rather
  than introducing a second freshness rule.
- Include safe source-coverage and semantic-index validation summaries. Do
  not expose raw stack traces, secrets, or provider credentials in the UI.
- Keep core mart freshness/parity separate from semantic-index coverage so
  an incomplete embedding index remains visible without misrepresenting the
  underlying reporting snapshot.
- Treat a missing snapshot, invalid timestamp, or failed source-to-mart
  validation as unavailable. Do not present synthetic zero-valued data as a
  fresh, successful result.
- Keep health display read-only. Manual sync remains Admin-only under the
  existing API policy.

### Evidence-backed AI insights

- Add a backward-compatible, structured evidence object to aggregate AI
  insights while retaining the existing `aiSummary` field for callers.
- Each displayed aggregate report identifies its reporting period and
  analytics snapshot, shows the supporting metric labels and values, and
  states material limitations. Evidence values are read from the snapshot,
  not generated by the model.
- Mark insights based on stale data as stale. Do not generate or refresh
  insights from a missing, invalid, stale, or source-to-mart-invalid
  snapshot. A previously generated insight may remain visible if explicitly
  marked stale.
- Persist a latest-revision AI insight job in DuckDB and debounce validated
  source changes for 30 seconds. Newer pending revisions replace older ones;
  one failed attempt is not retried until source data changes. On restart,
  reconcile an interrupted job against the saved insight and otherwise mark
  it failed without repeating a provider call.
- Expose job status through a read-only endpoint. The web UI distinguishes
  current, queued, generating, failed, waiting, and blocked states, and polls
  only while a job is queued or generating. Reloading the report remains a
  saved-result read and never triggers generation.
- Keep insights advisory. Do not create or update work orders, maintenance
  schedules, alerts, or operational records from generated content.
- Preserve the current response shape for work-order advisory endpoints and
  their assignment checks; those endpoints are not part of this response
  change.

## Settled decisions

- Source vehicle/schedule counts and every schedule-status total require
  exact parity; the aggregate maintenance-cost tolerance is less than 0.01.
- Embedding coverage must be 100% of eligible records. Three fixed synthetic
  vector queries must each retrieve their expected fixture within the top
  three results.
- Semantic-search validation is internal to the repeatable validator. This
  slice does not add a public semantic-search API or UI and does not claim
  natural-language relevance for operational records.
- Performance is recorded as a baseline with environment and dataset size;
  it is not a release gate until an owner sets a target runtime and threshold.
- Stale insights may remain visible with an explicit stale label. New
  generation is blocked when the snapshot is stale, missing, invalid, or
  fails source-to-mart validation.
- Use a durable single-job DuckDB queue with a 30-second quiet window rather
  than adding queue infrastructure. Keep deterministic analytics independent
  from provider calls; status reads and page refreshes remain non-generative.

## API, data, and migration impact

- Analytics remains a derived read model over core VMMS data. Core VMMS
  records remain authoritative.
- Add a fleet-role-protected `/analytics/data-health` endpoint. Reuse
  existing `generatedAt`, `sourceMaxUpdatedAt`, age, and stale metadata.
  Add evidence to aggregate insights while keeping `aiSummary` available to
  existing callers. Add a read-only `/analytics/insights/status` endpoint
  for durable job and saved-report state.
- Migration and validation changes are limited to the analytics DuckDB and
  pgvector data. No core VMMS schema change is proposed.
- No shared auth, portal, gateway, mobile, or cross-system API change is
  included.

## Security and failure behavior

- Preserve Admin/Operations access to fleet analytics and the server-side
  fleet-role guard from spec 0001. Keep sync Admin-only and preserve
  assignment-scoped work-order access.
- Do not treat analytics as authoritative for authorization, assignment, or
  current operational state.
- On migration, sync, validation, or provider failure, surface an explicit
  unavailable/error state. Never turn failure into a fresh zero report or
  unsupported AI claim.
- Keep generated insights advisory and validate every referenced value
  against the reporting snapshot.

## Acceptance criteria

1. Migrations are repeatable on clean and populated analytics stores, and
   failures do not publish partial data as a current validated snapshot.
2. For a fixed source snapshot, vehicle/schedule counts and every status
   total reconcile exactly; maintenance-cost totals differ by less than
   0.01.
3. Eligible embedding coverage is exactly 100%, and all three synthetic
   pgvector fixtures return their expected record in the top three.
4. Admin and Operations can distinguish current, stale, and unavailable
   analytics and can see snapshot/source times, age, source coverage, and
   semantic-index coverage.
5. Missing or invalid snapshots and failed source-to-mart validation never
   appear as a fresh all-zero report.
6. Aggregate AI insights retain the `aiSummary` field and include a validated
   reporting period, snapshot, supporting metrics, and limitations.
7. Stale insights are visibly marked, and new AI generation is blocked when
   the snapshot is stale, missing, invalid, or fails source-to-mart
   validation.
8. AI/provider failures are explicit and never result in invented metrics
   or operational writes.
9. Existing Admin/Operations fleet access, Admin-only sync, and
   assignment-scoped work-order policies remain unchanged.
10. Validated changes coalesce into one durable latest-revision job after a
    30-second quiet window. The status endpoint is read-only, the UI polls
    only while queued or generating, and interrupted/failed revisions do not
    cause duplicate provider attempts.
