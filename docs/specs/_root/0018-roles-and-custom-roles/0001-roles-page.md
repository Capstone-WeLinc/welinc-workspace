# 0018 child 0001. The Roles page (S20)

Part of [0018](index.md); builds against its shared contract (data model, API surface, value sourcing, security model). Repos: `welinc-auth` (read, history and members routes, `default_roles`), `welinc-web-portal`.

## Summary

The Permissions grid becomes the `Roles9` page: the role list on the left, one role on the right with Permissions, People and History tabs. Each permission is a switch with its plain description under the label, groups fold, and a small filter finds a permission. Changes in one or several roles collect in the navy save bar, are reviewed together in dialog RC (a note is required when anything is taken away), and are kept as a draft if you leave. A spreadsheet download replaces the old "compare" view.

## Requirements

**User stories**:
- As a suite admin, I want to open one role and see what it can do in plain words, so that I change it without scanning a grid.
- As a suite admin, I want to adjust two roles and save them in one review with one note, so that a related change lands together.
- As a system admin, I want to read my system's roles and move people into a role, so that I manage my staff without a suite admin.
- As an auditor or panelist, I want every role by every permission in one spreadsheet, so that I can check the whole setup at once.

**Acceptance criteria**:

*Page and list*
- **AC-1**: `/admin/roles/:system/:role` is one page on spec 0016's app shell, as on `Roles9`: the list pane beside the role, each scrolling on its own. `/admin/roles` and `/admin/roles/:system` open the first role of the viewer's first system (VRMS, VMMS, BMS order) with `replace`. `/admin/permissions` and `/admin/permissions?system=X` redirect to `/admin/roles/X` (or the first system). Selecting a role replaces the address. The portal sidebar item is "Roles" with the `IdCard` icon. A role code that isn't live shows "This role doesn't exist or was deleted." with a link to the system's first role. Below 768px the list and the role are separate screens, the role with a back link.
- **AC-2**: The list pane shows the title "Roles" with the count ("11 roles"), the system switch (a segmented control: a suite admin gets VRMS, VMMS, BMS; an admin of two or more systems gets their systems; an admin of one system gets none), a search field (matches role name and description, ignoring case), and the sticky headings "Built in" and "Custom" (Custom shows only when `supportsCustomRoles`, with "No custom roles yet" under it when empty). Each row shows a square initials tile, the name, and the people in words ("8 people", "1 person", "No one yet"); the selected row is filled as on `Roles9`. A search with no match shows spec 0016's no match state with Clear.
- **AC-3**: The role header shows the 40px square initials tile, the name in `text-title`, the `RoleChip` (filled "Built in", outlined "Custom"), the description, and one help line ("Comes with VRMS. You can change its permissions, not delete it." or "Made by a suite admin. You can rename or delete it."). Facts: People (count), Permissions ("19 of 28", mono; the total is the number of keys, umbrella value sourcing), Last changed ("[date] by [name]", or "Not changed yet"). Header actions for a suite admin: the ⋮ menu "More role actions" with Reset to defaults on a built in role (AC-10); child 0002 adds Duplicate, Rename, Edit description and Delete. Tabs: Permissions (count "19/28"), People (count), History, spec 0016 tabs. A system without permissions shows only the People tab, and its help line reads "VMMS sets what each role can do in its own app. You can give these roles to people here."

*Permissions tab*
- **AC-4**: Groups follow the catalog order and fold (spec 0016 fold motion). Each group header shows the name, "allowed/total" in mono, and when folded a preview ("See every ticket, Assign mechanics and 6 more", "None" when empty). The first group is open the first time a role opens; "Open all" or "Close all" sits above the groups. Each row shows the label (500), its description under it in `text-small` `muted-foreground`, and a spec 0016 `Switch` labelled by the label. A locked cell (`lockedRoles` holds this role) shows "Always on" or "Always off" with a lock icon instead of a switch. A changed row uses `draft-row` with the "Not saved" tag.
- **AC-5**: A "Find a permission" field sits above the groups. Typing (300ms after the last key) keeps only rows whose label or description contains the text (ignoring case), opens every group with a match, and hides groups without one; clearing it restores the folds as they were. No match shows "No permission matches "[text]"" with Clear. The text isn't kept in the address or the draft.
- **AC-6**: A viewer who isn't a suite admin (`canEdit` false) sees the same rows with "On" or "Off" in place of switches, no save bar, no Reset to defaults, no ⋮ edits. The spreadsheet download and Add people (AC-13) follow their own rules.

*Saving*
- **AC-7**: Flipping a switch records `{ role, key, from, to }` in one draft per system; flipping it back removes the entry. The gold draft bubble (`DraftMarks` B) shows on every role row with entries, the current one included, with the count and the accessible name "[n] unsaved changes". The spec 0016 `SaveBar` appears on the first change: "[n] unsaved changes", plus " in [m] roles" when more than one role is touched; the sub line is the role names joined ("Chief mechanic and Parts clerk") plus " · affects [p] people" (the sum of their `peopleCount`) or " · no one holds it yet". Discard clears the whole draft.
- **AC-8**: The bar's change list follows `SaveBar9`: header "Changes to [role]" for one role or "Changes to [m] roles" with the role names as sub headings, then the permission groups under `text-label` names, each row a `+` or `−` tile, the label, "~~Off~~ → On" and a labelled Undo ("Undo See every ticket"); the quiet mono "+a −r" in the header; at the bottom, up to three faces and "Ramon, Alfredo and 6 more get this the next time they open VRMS" per role (or "No one holds Parts clerk yet").
- **AC-9**: "Review and save" opens dialog RC: title "Save [n] changes?"; one block per role with its faces line, its permission groups folded with "+a −r", and the changed items. When any change takes something away, the note field "Note for the activity log" starts open, is marked required, and Save stays disabled until it holds a non blank reason (at most 500 characters); otherwise it stays folded behind "Add a note for the activity log" and is optional. When a custom role would hold `team.manage` or `settings.manage` after the save, its block shows the warning "[Role] can manage the team and change settings in [system].". Buttons: "Keep editing", "Save [n] changes" ("Saving…" while it works).
- **AC-10**: "Reset to defaults" (built in role, suite admin) adds to the draft every unlocked cell whose value differs from its catalog default (`defaultRoles`), as ordinary changes you review and save; when nothing differs it is disabled with "Already on the defaults".
- **AC-11**: Saving sends one `PATCH /auth/admin/permissions/:system` with every draft cell, the read `version` and the note. Success: the draft and the stored draft clear, the page reads the role data again, and the toast "Saved [n] changes to [system] roles." shows. A 409 `MATRIX_STALE` closes the dialog, reads the latest data, keeps the draft entries whose `from` still matches the server, drops the rest, and shows the warning toast "Someone saved [system] roles while you were editing. Your changes that still apply are kept. Check them and save again." A 409 `LOCKED_CELL` or 400 `UNKNOWN_ROLE` reads the latest data, drops those entries and shows an error toast naming the permission or role. A network error keeps the dialog open with the error inline and Save enabled. Every time the page reads the role data (load, after a save, after a conflict), draft entries for a role that is no longer live are dropped, with the toast "[n] changes to a role that was deleted were removed from your draft."; a role renamed elsewhere keeps its entries (the draft is keyed by code) and shows its new name.
- **AC-12**: Drafts follow spec 0016 *Saving and drafts*: stored under `welinc:draft:<user id>:roles:<system>` with the time and each `from`; leaving the page shows "Your [n] changes to [role, or "[system] roles" when several] are kept for when you come back"; coming back restores them with the bar sub line "Kept from [time]"; a stored `from` that no longer matches the server drops the whole draft with the toast "Your saved draft for [system] roles was out of date, so it was cleared."; drafts expire after 7 days and clear on sign out; closing or reloading the tab gets the browser's prompt. Switching systems keeps each system's draft separately.

*People, History, download*
- **AC-13**: The People tab lists the role's holders sorted by name, 25 at a time with Load more: round initials tile, name, email, "Since [date]" (the role row's `createdAt`), and "Until [date]" for a temporary holder. Each row opens the person on People (`/admin/people/:id`, spec 0017). Empty: "No one has this role yet" and "Use "Add people" above, or change a person's role from their page." An "Add people" button shows for a suite admin or an admin of the system (not on a role in a system the viewer can't change roles in).
- **AC-14**: Add people opens a dialog "Add people to [role]": a search over people in the system who don't hold this role (name or email), several can be picked, each picked row shows "[current role] → [role]" (or "Until [date] · temporary, can't be moved" disabled for a temporary holder; the viewer and suite admins are left out). Save ("Moving…") sends the members route; success toasts "[n] people now have [role]." and refreshes the tab, the counts and the list. When the role is the system's admin role, the password step (`ReauthDialog`, purpose `ADMIN_ACTION`) runs first. Candidates come from the server (`excludeRole`, `assignable=true`, sorted by name, 25 at a time with Load more), so the holders, the viewer and suite admins never show. Errors show inline: `LAST_ADMIN` "[Name] is the last active admin of [system]. Make someone else admin first.", `TEMPORARY_ROLE` "[Name]'s role is temporary and ends by itself.", `ROLE_LIMIT` the server's message; nothing moves when any person fails.
- **AC-15**: The History tab lists the role's history newest first, 25 at a time with Load more: the actor ("System" for the catalog sync), what happened ("added "Use AI diagnosis"", "removed "Encode costs"", "created the role from Chief mechanic", "renamed it from Parts clerk to Parts and costs clerk", "changed the description", "deleted the role"), the note in quotes under it when present, and the date and time in mono. Empty: "No changes yet". The cell rows a create or delete writes are not listed one by one (the umbrella's History rule).
- **AC-16**: The list pane's ⋮ "More options" holds "Download as spreadsheet" (anyone who can read the page, systems with permissions only). It builds a CSV in the browser from the saved data (never the draft): UTF-8 with a byte order mark, columns Group, Permission, Description, then one column per live role in list order (headed by name, custom ones suffixed " (custom)"), cells "Yes" or "No"; a last row "People" with each role's count. Every cell is quoted, and a cell starting with `=`, `+`, `-` or `@` gets a leading `'` so a spreadsheet never runs it as a formula. File name `welinc-<system lower>-roles-<YYYY-MM-DD>.csv` (the viewer's local date). The download runs from a click handler with an object URL, so it works in the portal (not an artifact frame).

*welinc-auth*
- **AC-17**: `GET /auth/admin/roles/:system` and `/history` answer as in the umbrella's contract, `Cache-Control: no-store`. `catalog:sync` writes `system_permissions.default_roles` from each permission's `defaults`; the migration fills it once. Each `roles[]` entry of the admin people routes (spec 0017) gains `createdAt`. The members route locks the target role row and, when the move takes anyone off the system's admin role, the admin role's holders, then moves every listed person in one transaction with spec 0017's role change rules (each person's roles in that system are replaced by this one, as Change role does); `LAST_ADMIN` is judged on the end state of the whole batch, and the password step applies only when the target is the admin role; writes the same account events and directory changes as a single role change per person, skips people who already hold the role (`skipped`), and answers 400 `NOT_IN_SYSTEM` (any listed person holds no role in the system), `SELF_ROLE`, `SUITE_ADMIN_NO_ROLES`, `UNKNOWN_ROLE` (the role isn't live), `REAUTH_REQUIRED` (admin role without a valid `reauthToken`), 409 `TEMPORARY_ROLE`, `LAST_ADMIN`, `ROLE_LIMIT`. The admin people list (spec 0017) gains `excludeRole` and `assignable` (umbrella API table). `catalog:sync` treats `default_roles` like any other catalog field: it is part of the plan, the dry run output and the no change check, with tests in `permission-plan.spec.ts`; a built in role added to the catalog later updates `default_roles`, and Reset to defaults always uses the current value.

*Quality*

Lint, typecheck, `build:local` and the tests pass in the portal; lint, build, tests and `npm run openapi:check` in welinc-auth; `node scripts/check-contract-routes.mjs` passes after the OpenAPI file is regenerated.

## Feature design

**Components** (portal, `src/pages/admin/roles/`): `RolesPage` (route, data, draft), `RoleList`, `RoleDetail` (header, tabs), `PermissionGroups` (folds, filter, rows), `RolePeople`, `AddPeopleDialog`, `RoleHistory`, `RoleReviewDialog` (replaces `MatrixReviewDialog`), `downloadRolesCsv.ts`. The draft logic in `matrixDraft.ts` stays (keys `role|key`) and gains the stored draft through spec 0016's draft hook. `PermissionsView`, `MatrixReviewDialog` and `MatrixHistory` are retired once the page ships.

**Key invariants**:
- One draft per user and system; the page never saves anything without the review dialog.
- A note is present on every save that takes a permission away (client and server).
- Locked cells never enter a draft.
- The download and the counts use saved data only.

**Critical test scenarios**:
- Happy path: `suite.admin@` opens Roles, turns on "Encode costs" for Chief mechanic and off "See every ticket" for Mechanic, sees "2 unsaved changes in 2 roles", reviews (note required), saves; History of both roles shows the note, verifies **AC-7**, **AC-9**, **AC-11**, **AC-15**.
- Stale save: a second session saves first; the first gets the warning toast and keeps only still valid entries, verifies **AC-11**.
- Draft: change two switches, open People, come back; bar shows "Kept from [time]"; change the server meanwhile and the draft clears with its toast, verifies **AC-12**.
- Read only: `vrms.admin@` sees On and Off text, no bar, Add people on People; `bms.admin@` sees only People with the help line, verifies **AC-3**, **AC-6**, **AC-13**.
- Add people: `vrms.admin@` moves two mechanics into Chief mechanic; moving the last admin answers `LAST_ADMIN` and nobody moves, verifies **AC-14**, **AC-17**.
- Filter: "cost" shows See costs, Encode costs and Add receipts (its description mentions costs) across one open group, verifies **AC-5**.
- Download: the CSV opens in a spreadsheet with one row per permission plus People and one column per role; a role named "=SUM(1)" stays text, verifies **AC-16**.

## Rationale (short)

Role first editing matches how admins think ("what can a Chief mechanic do?") and survives a longer role list, which a 27 by N grid doesn't (the reasoning from the Nov 18 rounds). Saving several roles in one review keeps a related change (give Chief mechanic costs, take them from Mechanic) atomic, and the API already accepted cells for several roles. Descriptions sit under each label because the switch's effect matters more than density (you picked it on the mockup). The note stays required on removals because taking access away is the change people ask "why?" about later. The spreadsheet replaces the compare view you dropped in round 8 at almost no cost. Add people only moves people already in the system, so it never duplicates S19's Add person dialog.
