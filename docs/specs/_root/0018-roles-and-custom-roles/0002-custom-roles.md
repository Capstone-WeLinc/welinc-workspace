# 0018 child 0002. Custom roles (S21)

Part of [0018](index.md); builds on child [0001](0001-roles-page.md) and the umbrella's shared contract. Repos: `welinc-auth`, `welinc-web-portal`, `welinc-backend-vrms`, `welinc-web-vrms`, workspace (contract 0001).

## Summary

A suite admin can make a new role for a system that uses WeLinc permissions (VRMS today) by copying an existing role, then rename it, edit its description, give it to people, and delete it once no one holds it. Built in roles stay fixed: no rename, no delete. For a custom role to really work, VRMS stops reading role names: it takes permissions for every live role, decides who can be assigned tickets by a new permission "Can be assigned tickets", and shows role names from the catalog. The shared mobile app keeps accepting only Mechanic and Chief mechanic, so custom roles work from the browser.

## Requirements

**User stories**:
- As a suite admin, I want to make a "Night shift lead" by copying Chief mechanic and taking away cost access, so that the role matches how the garage really works.
- As a VRMS admin, I want to give a custom role to my staff like any other role, so that custom roles need no special handling.
- As a mechanic in a custom role such as "Tire specialist", I want VRMS to work for me exactly as my permissions say.

**Acceptance criteria**:

*Portal*
- **AC-20**: For a suite admin on a system with permissions, the dashed "New role" button pinned at the bottom of the list opens the dialog "New role": Name (required), Description (optional), "Start from" (a select of the system's live roles, default the role on screen, help text "Its permissions are copied. You can change them after."). "Create role" ("Creating…") sends `POST /auth/admin/roles/:system`. Success: the toast "[Name] created from [source]." shows, the list refreshes, the new row gets spec 0016's landing flash, and the new role opens on its Permissions tab. When the source holds unsaved changes, the dialog says "Unsaved changes on [source] aren't copied." When the source holds `team.manage` or `settings.manage`, it warns "[Name] will be able to manage the team and change settings in [system].". The page takes the new role's cells and the new `version` from the create answer, so a later save isn't refused as stale.
- **AC-21**: "Duplicate" (an outline button in the role header, suite admins, systems with permissions) opens the same dialog titled "Duplicate [role]" with Name prefilled "Copy of [role]" (cut to 40 characters) and "Start from" fixed to that role.
- **AC-22**: Name is trimmed, 2 to 40 characters, holds at least one letter A to Z or digit (the code is made from those, umbrella rules), and is unique among the system's live roles ignoring case; description is at most 200 characters. Inline errors: "Name needs 2 to 40 characters.", "Use letters or numbers in the name.", 409 `ROLE_NAME_TAKEN` "There's already a role called [name] in [system].". With 20 live custom roles, New role and Duplicate are disabled with "[system] has 20 custom roles, the most it can have. Delete one to make another." and the server answers 409 `CUSTOM_ROLE_LIMIT`.
- **AC-23**: A new role gets the source's saved cells for every permission (not any draft). Locks belong to the roles named in the catalog, so a cell locked for the source is an ordinary editable cell on the copy, starting at the source's value. The copy is never the admin role. `copied_from` keeps the source code, `created_by_id` the creator, and a `CREATED` role event records the source name; each copied cell is written to `permission_changes` (before null, after the value, actor the creator, note "Created from [source]"), and the matrix version rises once.
- **AC-24**: On a custom role, the ⋮ menu holds Rename and Edit description; each opens a small dialog with one field and Save ("Saving…"). Success toasts "Renamed to [name]." or "Description saved." and writes a `RENAMED` or `DESCRIBED` role event with the old and new values. The code never changes, so tokens and VRMS data are untouched. Built in roles show neither item (`PATCH` answers 400 `BUILT_IN_ROLE`).
- **AC-25**: "Delete role" (custom only, destructive, last in ⋮) follows `Confirm6` DB. With live holders (umbrella rule): the alert dialog "[n] people still have [role]", "Give them another role first. Then you can delete it. No one loses access by surprise.", up to 10 holders each with "Change role →" (opens the person's Access tab, spec 0017), "and [k] more" opening the People tab, Close, and "Delete role" disabled. With none: "Delete [role]?", "No one has it. Its history stays on record.", Cancel and Delete; when people in their deletion grace period still hold it, the dialog adds "[k] people waiting for deletion keep it until their deletion completes; if one is restored, they come back without it." The server checks again and answers 409 `ROLE_IN_USE` with the count, which the dialog then shows. Success archives the role (`deleted_at`), removes its cells (logged to `permission_changes` with after null and the actor), writes a `DELETED` role event, raises the matrix version, drops the role's entries from the stored draft, opens the system's first role and toasts "[role] deleted.".
- **AC-26**: Built in roles have no Rename, Edit description or Delete anywhere; Reset to defaults stays (child 0001, AC-10). Custom roles have no Reset to defaults.
- **AC-27**: A system without permissions (VMMS, BMS today) shows no Custom heading, no New role and no Duplicate; `POST /auth/admin/roles/:system` answers 409 `CUSTOM_ROLES_NOT_SUPPORTED`.
- **AC-28**: A live custom role can be chosen wherever a role is chosen: spec 0017's Change role and Add person dialogs, child 0001's Add people, and Temporary access (spec 0013). Everywhere a role chip shows, a custom role uses the outlined `RoleChip`. `maxRolesPerUser` still applies.

*welinc-auth*
- **AC-29**: A custom role travels like any role: its code in the access token's `roles`, `/auth/me`, the directory feed and the `/auth/users*` routes (which already check roles against the database). `/auth/systems` lists live roles with `builtIn`, built in first by `sortOrder`, then custom by name; archived roles never appear in tokens, pickers or the permission poll, and a person can't be given one (400 `UNKNOWN_ROLE`). Contract 0001 gets a new minor version whose Changes line names `builtIn`, runtime role codes for systems with permissions, and the 0018 admin routes.
- **AC-30**: `catalog:sync` plans only `is_built_in` rows: it never updates, deletes or refuses because of a custom role (live or archived), it never checks role names, and it refuses a catalog file code starting with `C_` ("Codes starting with C_ are kept for custom roles"), so a catalog code can never meet a custom one. The migration leaves the 12 existing roles built in, and the sync's no change check still passes after it.
- **AC-31**: The `vmms-mobile` OAuth client is unchanged: for VRMS it still allows MECHANIC and CHIEF_MECHANIC only (`prisma/seeds/clients.seed.ts`), because the mobile app decides its screens by those codes, not by permissions. A custom VRMS role signing in to the mobile app gets the existing `APP_NOT_ALLOWED` answer. The role's help line on the Roles page adds "Works in the browser. The mobile app is for Mechanics and Chief mechanics." for custom VRMS roles.

*VRMS*
- **AC-32**: welinc-backend-vrms takes cells for every role in the `/auth/permissions/VRMS` answer: `MATRIX_ROLES` and `isMatrixRole` go (`src/auth/permissions/catalog.ts`), and their users follow (`permissions.service.ts` `keysFor` and its other read, `permission-matrix.service.ts`, the sync's `matrix-rows.ts`); `RolePermission` rows of a role no longer in the answer are removed on the next sync. Inside `keysFor`, a VRMS role code the last sync doesn't know triggers one sync at once (at most once per 10 seconds across the process) before deciding; a code still unknown gets no keys (403 as today, logged as `permission_denied`). The VRMS matrix copy endpoint lists every synced role.
- **AC-33**: The VRMS catalog in welinc-auth gains `ticket.assignable` ("Can be assigned tickets", group Tickets, "Shows up in the mechanic list, so tickets can be assigned to you.", defaults Admin off, Chief mechanic on, Mechanic on), and VRMS's `catalog.ts` gains the key. The mechanic roster (`mechanic-roster.service.ts`) holds every VRMS person whose roles grant `ticket.assignable` in the synced grants: `roleOf` and the per request `ensure()` become key based, and the roster is recomputed after a directory change and after a permission sync that changes any `ticket.assignable` or `ticket.verify` cell. **Nothing recomputes until the first permission sync of the process has loaded and `ticket.assignable` is present in it**; until then the roster stays as stored, so a cold start or the deploy gap never empties it. `Mechanic` gains `assignable` (`boolean NOT NULL DEFAULT true`): someone who loses the key gets `assignable = false`, stays on their open tickets, keeps showing in history filters and the dashboard (`isActive` is untouched), and isn't offered in assign pickers or `view=mine`; `isActive` keeps meaning "still a VRMS person". With the built in roles only, the roster holds exactly the same people as today (a test compares both rules on the seed).
- **AC-34**: Nothing in welinc-backend-vrms or welinc-web-vrms decides behaviour by a VRMS role code: `Mechanic.role` keeps the person's role code (the CHECK limiting it to MECHANIC or CHIEF_MECHANIC is dropped, the column becomes `varchar(30)`); where a screen or rule meant "chief" it uses `ticket.verify`, computed from the synced grants at recompute time and stored on the roster row as its lead flag (the dashboard Team section label, `mechanic-work.service.ts`; `isMechanic` in user management uses roster membership); the audit trail's `actorRole` takes the person's VRMS role with the most allowed keys (ties by built in order, then by name) and the audit role filter lists the live roles from the catalog; the `'MECHANIC'` fallback in `session.ts` is removed (no VRMS role shows the no access page). The full list to change: backend `src/auth/roles.ts`, `mechanic-roster.service.ts`, `mechanic-work.service.ts`, `audit-events.ts` (`AuditRoleFilter` and the widest role pick), the test fakes (`account-check.fake.ts`, `verify/testing/test-auth.ts`); web-vrms `types/index.ts` (role becomes `string`), `features/user-management/lib/accountStatus.ts`, `lib/api/vrmsConfigApi.ts`, `lib/api/activityApi.ts`, `lib/activity/activityFormat.ts`, `components/activity/ActivityRows.tsx`, `features/dashboard/components/TeamSection.tsx`, `lib/session/session.ts`; a final search for the three quoted codes outside seeds and tests finds none.
- **AC-35**: web-vrms shows role names from `GET /auth/systems` (through the gateway; now `Cache-Control: no-cache` with its ETag, so each read revalidates cheaply), read on load and again on focus after 60 seconds, falling back to the code in title case; `RoleBadge` uses the neutral chip for every role (spec 0016, AC-15). Tests that list the three codes are updated.

## Feature design

**State of a role**: live built in (from the catalog, never archived) · live custom → archived (Delete, only with no holders). No way back from archived; a new role with the same name gets a new code.

**Key invariants**:
- A custom role is never `is_system_admin` (database CHECK).
- A code is never reused within a system, so history and VRMS's audit rows never point at the wrong role.
- Archived roles hold no cells and no live holders.
- The sync and the runtime never fight: the sync owns built in rows, the runtime owns custom rows.
- In VRMS, every behaviour difference between roles comes from permission keys.

**Critical test scenarios**:
- Create and use: `suite.admin@` creates "Tire specialist" from Mechanic (code `C_TIRE_SPECIALIST`), turns off "Use AI diagnosis", gives it to a seed mechanic; their token holds the new code, VRMS answers their tickets and refuses AI, verifies **AC-20**, **AC-23**, **AC-29**, **AC-32**, **AC-36**.
- Name rules: "chief MECHANIC" is refused as taken; "!!" is refused; a 40 character name gives a code of at most 30; the 21st custom role is refused, verifies **AC-22**.
- Delete blocked then allowed: delete with 2 holders shows the DB dialog; after moving them, delete archives it; History still shows "deleted the role"; the code isn't reused by a new "Tire specialist", verifies **AC-25**.
- Sync safety: with a custom role held, `npm run catalog:sync` reports no change and `db:deploy` passes; a catalog code starting with `C_` is refused; a built in renamed in the catalog to a custom role's name syncs fine, verifies **AC-30**.
- Roster parity: before any custom role, the roster by `ticket.assignable` equals the roster by codes, verifies **AC-33**.
- Fresh role in VRMS: a person given a role created 5 seconds ago gets their keys on the first request, verifies **AC-32**.
- Mobile: a custom VRMS role gets `APP_NOT_ALLOWED` from the shared mobile app, a Chief mechanic still signs in, verifies **AC-31**.
- Cold start: restart welinc-backend-vrms with the permission sync failing; the roster is unchanged until the first successful sync, verifies **AC-33**.
- Races: a Delete and an Add people on the same role at once; either the move lands and Delete answers `ROLE_IN_USE`, or Delete lands and the move answers `UNKNOWN_ROLE`, verifies **AC-25**.
- Other systems: a VMMS person with a `C_` VRMS role uses VMMS normally, verifies **AC-37**.
- VMMS: `POST /auth/admin/roles/VMMS` answers 409 `CUSTOM_ROLES_NOT_SUPPORTED`, verifies **AC-27**.

## Rationale (short)

Custom roles only make sense where a role's permissions are the whole truth about what it can do. That's true in VRMS once its few role code checks move to permissions, and false in VMMS and BMS, where about 150 checks name role codes (the role usage map gathered for this spec). So custom roles are offered per system by the presence of permission keys, and VRMS pays the small cost of moving its checks. Copying from an existing role was chosen over starting empty because almost every custom role is a tweak of a built in one. Archiving instead of deleting keeps history readable and stops a code from being reused for a different meaning. Built in names stay owned by the catalog so seeds, papers and the other systems' labels never drift. The mobile client keeps its fixed list because the mobile app picks its screens by role code and doesn't use permissions; feature 48 decides whether that changes.
