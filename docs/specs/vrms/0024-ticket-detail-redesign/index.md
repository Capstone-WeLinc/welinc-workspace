# 0024. Ticket detail page around foldable issue rows

**Date**: 2026-11-06
**Status**: In Progress

## Summary

The repair ticket page is rebuilt around the work. Each issue becomes a row that folds open and closed (an accordion), showing its progress and state when closed, so a ticket with 10 issues and up to 20 steps each stays readable. Reference clutter goes (typical parts and hours), photos get their own card after the issues with one add control that says where the photo lands, AI and Activity fold to one line, and no part of the page is joined by a dot, the title follows the design file, Cancel ticket moves into a menu, and on phones the issues come before people and details. It is mostly a web change on data the page already has. Task 8 adds one optional field to the photo upload and narrows Before photo protection on the server (no new endpoint, no migration).

## Requirements

**User stories**:
- As a mechanic on my phone, I want the issue I am working on open and the rest folded, so that I tick steps without scrolling past finished work.
- As a verifier, I want every issue folded with what fixed it on the row, so that I can sign off a whole ticket from one screen.
- As an Admin, I want the page to look like a well made work order, plain where it can be and coloured only where it means something, so that the important things stand out.
- As anyone, I want the plate and the main issue as the title, so that I know which truck I am looking at.

**Acceptance criteria**:

Issue rows
- **AC-1**: Issues render as one list of foldable rows (shadcn Accordion, `type="multiple"`), split by thin dividers inside the Issues card, with no bordered box inside a row. The whole row header is one button (`aria-expanded`, `aria-controls`, at least 44px tall on phones), inside an `h3`, and folding uses the `ease-snappy` curve (none with reduced motion).
- **AC-2**: A closed row is at most two lines. Line 1: the issue number, the issue text (semibold, one step above body text: `text-base` from 768px, `text-sm` on phones) (2 lines at most on phones, 1 from 768px, cut with an ellipsis), and on the right the progress and the chevron. Line 2, muted `text-xs`, its parts split by space only (`gap-3`, never a dot or other symbol): the category, then "Known fix: {name}" or "No known fix", then the word "Safety" in the warning colour when the linked known fix has safety notes (trimmed, not empty). The known fix name is plain text here (never a link: the header is one button with no controls inside), with its status badge when the entry is Draft or Inactive. Once the issue has a saved resolution, a closed row's line 2 shows "What fixed it" instead (an open row keeps the category, known fix and Safety line, since the resolution block shows below it, AC-7): the note, else "Followed the known fix" when `followedKnownFix`, else nothing, cut to 1 line, then the hours as "2.5 h" when `hoursSpent` is set, split from the note by space. A Done issue with no saved resolution while the ticket is In progress shows "Needs what fixed it" in muted text at the end of line 2. Once a resolution is saved, line 2 holds only What fixed it and the hours (no category, known fix or Safety word); the safety line inside the open row (AC-8) still shows. "Needs what fixed it" shows only while the ticket is In progress, never in On hold, Outsourced, Pending approval or later.
- **AC-3**: The issue's state (derived, nothing stored) shows as the progress text with a slim bar under it (4px, full width of the progress column):
  - **Returned**: the issue has a saved resolution but no `resolvedAt` (spec 0014); gold `highlight` text "Returned", bar hidden. Wins over every other state.
  - **No checklist**: the issue has no steps; muted text, no bar.
  - **Not started**: steps exist, none ticked; muted "Not started", empty bar.
  - **In progress**: some ticked; "{x} of {y}" in tabular figures, bar in the In progress token.
  - **Done**: all ticked; "Done" in the `success` colour, full bar in `success`.
  The progress column has a fixed width (`w-24`, inside the fold button, before the row menu), its text right aligned and its bar the column's full width; every state reserves the width, No checklist and Returned included, so the state words line up on every row.
  Ticks made on this page count at once: the local tick overrides move up from `IssueBlock` into one `useTickOverrides` hook for the whole list (keyed by step id, cleared for an issue when its `checklistVersion` changes, and an override dropped once the server value equals it), so the closed row, the summary line and the open rule all read the same merged steps (`mergedSteps` in `lib/issueRow.ts`). The overrides live outside the folding content, so folding a row never drops a pending tick or its rollback. Returned rests on the rule that resolution notes are saved only on the move to For verification, so notes without `resolvedAt` mean the ticket came back.
- **AC-4**: Which rows start open, on a first visit to this ticket in this tab: while the ticket is Open, Assigned, In progress, On hold, Outsourced or Pending approval (an allow list in `initialOpen`, not "every other status"), the first row that is not Done and not No checklist opens (a Returned row counts as not Done), and every row opens when the ticket has 3 issues or fewer; in For verification, Closed and Cancelled every row starts closed. The rule depends on status only, not role. Issue order is the array order the ticket response sends (by `createdAt`, then `id`; a backend test locks it). A link with `#issue-N` (N from 1, today's order) opens that row on top of whatever is open or stored, and scrolls it into view once per hash value (rows carry `scroll-margin-top` for the sticky header); an N out of range is ignored.
- **AC-5**: Open and closed rows are remembered per ticket in `sessionStorage` (`vrms.ticket.<id>.view`, shape `{ open: string[] }`, checked when read, at most the 20 most recent tickets kept). The open value lives in `useTicketView`, never derived from props, and drives the Accordion as a controlled `value`. A stored state wins over AC-4 on a reload. The 3 second refresh never opens or closes a row; an issue that appears later starts closed; a removed issue drops out of the stored state. If storage fails, the page uses AC-4 and keeps state in memory. An older stored shape still reads: its `open` list is kept when valid, and any `hideDone` field (boolean, list or anything else) is ignored and dropped on the next write. The 20 ticket prune stays.
- **AC-6**: Above the rows, one line: "{d} of {n} issues done, {t} of {s} steps ticked" (the step part counts only issues with steps and is left out when none have steps; "1 issue" and "1 step" in the singular). The line has no controls: no Hide done steps switch, no Expand all or Collapse all. Each row's header opens and closes it, and the open rows are remembered (AC-5).

Inside an open row
- **AC-7**: Top to bottom: the safety note, the checklist, one quiet "Edit steps" (or "Add steps") text button, then the resolution. Shown read only, the resolution is one block: a small "What fixed it" label with the hours ("3.5 h") on the right of that line only when `hoursSpent` is set, then the note (or "Followed the known fix") under it; no separate "Hours spent" field and no "—". The issue's other actions sit in a `⋮` row menu (`dropdown-menu`, 44px target on phones) on the row header line, between the progress column and the chevron, shown whether the row is open or closed: Edit issue and Remove issue (spec 0019, Remove in `destructive` text), Change known fix (relink, spec 0007, only when the issue may be relinked) and Open known fix (`/knowledge-base/<entryId>`, only while `knowledgeOn`). Each keeps its current `can` rule; the `⋮` is not shown when the menu would be empty. Choosing Change known fix shows the link picker inline in the row with "Remove link" and "Keep it". Edit issue and Remove issue follow `canEditDetails` (the edit flag and `ticketEditable`, as today); Remove is hidden when the ticket has one issue (spec 0019, AC-17). The menu trigger is a sibling of the fold button inside the row header, never inside it (the header stays one button with no controls inside): `AccordionTrigger` gets an `actions` slot rendered inside the Radix `Header` after the button, and the row's chevron moves out of the button to sit after the actions (`aria-hidden`, clicking it toggles the row, like `FoldCard`'s); and it is named "More actions for issue {n}" and shows a "More actions" tooltip on hover and focus.
- **AC-8**: The safety note is one line of `warning` tinted text (no box, no icon) above the checklist, cut to 1 line (`line-clamp-1`) with "More" shown only when the text is actually cut off, expanding it in place. It never hides behind a fold other than the row itself, and the closed row's "Safety" word (AC-2) points to it.
- **AC-9**: The checklist keeps its ticks, rules and tags (specs 0007, 0021, 0023). Done steps show dimmed (no strikethrough) and always stay in the list; nothing hides them. Step rows are at least 44px tall on phones and 36px from 768px.
- **AC-10**: Typical parts and typical hours are no longer shown on the ticket, and the open row has no separate known fix line: the name is on line 2 of the row header (AC-2) with its status badge when Draft or Inactive, and Open known fix and Change known fix live in the row menu (AC-7). An issue with no known fix keeps the link picker (when it may be linked) and "Suggest a known fix" inline in the open row.

Page
- **AC-11**: The title is the plate chip, then the model when `vehicleModel` is set, then the first issue's text (cut to 1 line; left out when the ticket has no issues); the ticket ID sits below in `muted-foreground`, never breaking. - **AC-12**: Issue text never shows the stored `[System] ` prefix anywhere on the page (rows, title, dialogs such as Edit steps); the category shows once, from `categoryName`. Where the page shows issue text (rows and title), a repeated root cause shows once: the text is split at its first ": " into root cause and description, and when the description starts with the root cause (case insensitive, after trimming), that repeat and any following spaces, commas, periods or colons are dropped ("Aircon not cooling: Aircon not cooling, blows warm air." reads "Aircon not cooling: blows warm air."); with nothing left only the root cause shows; with no ": ", or text that starts with ": ", the text is unchanged. The match needs a whole word: the description must equal the root cause or continue with a non letter or digit right after it (a space, comma, period or colon counts). So "Aircon: Aircon cooling weak" reads "Aircon: cooling weak", while "Air: Aircon cooling weak" stays unchanged, since "Air" is only part of the word "Aircon". Photo groups on the server (amends spec 0018)
- **AC-21**: The photo upload (`POST /vrms/repairs/:id/attachments`, spec 0017) takes an optional multipart field `group`, `BEFORE` or `AFTER`, for photo uploads only (a document kind with `group`, or any other value, answers 400). Absent, the server picks the group from `workStartedAt` as today (spec 0018, AC-1). Present, the photo is stored as `VEHICLE_PHOTO` (Before) or `PROOF` (After), decided under the ticket row lock where today's pick runs; the same add right (`ticket.files.add`), the duplicate check across both photo kinds, and that group's cap (409 when full) apply as today, and the `ATTACHMENT_ADDED` audit row records the stored kind. Either group is allowed whatever `workStartedAt` says, matching Move (spec 0018, AC-9). `group` overrides the pick for every photo kind the upload accepts (`PHOTO`, and the older `VEHICLE_PHOTO` and `PROOF`, which read as `PHOTO`). Order of checks: the ticket's visibility and finished check stay first; then the 400 for `group` on a document or a bad value (the DTO has `@IsOptional() @IsIn(['BEFORE', 'AFTER'])`, the service rejects it on a document); then the rest of the first failing check order (spec 0017, AC-12b) runs with the group's kind as `earlyKind`, and the kind under the lock is the group's kind too. The web sends `group` only for a drop on a zone; the add tile and the file picker send none.
- **AC-22**: Before photo protection (spec 0018, AC-10) follows the upload time only: a `VEHICLE_PHOTO` is protected when `tickets.protect_before_photos` is on, work has started, and its `createdAt` is at or before `workStartedAt` (inclusive; both are server times, `createdAt` set inside the upload's lock). Move never changes `createdAt`, so a photo uploaded before work started stays protected wherever it moves back to Before, and a photo uploaded after work started is never protected in Before, whether it was dropped there (AC-21) or moved there. Such a late Before photo carries a new mark `addedAfterWorkStarted` in the attachment view, shown as "Added after work started" (AC-13, Marks), to everyone who sees the photo (not gated like `takenBeforeWork`'s verifier view), so the uploader sees why Remove works and the verifier sees it is not pre-work evidence. One pure `isAddedAfterWorkStarted(row: { kind, createdAt }, workStartedAt: Date | null)` beside `isTakenBeforeWork` decides it; `isProtectedBefore` takes the row's `kind` and `createdAt` and the ticket's `workStartedAt` (replacing the `workStarted` boolean in its rights) and returns false whenever `isAddedAfterWorkStarted` is true; `canRemove` and `canMove` pass those through.

## Decision

**Chosen option**: Option 1: Foldable issue rows on the existing page, built on the data the page already has.

The Issues card becomes an accordion of issue rows with a derived state, the reference clutter goes, and the side sections move to follow the design file, without any backend change.

## Feature design

**Data model sketch**: none. No schema change. Every value comes from the ticket response, the file list and the latest diagnosis the page already loads.

**State transitions**: none on the server. The issue state of AC-3 is derived on each render; its precedence is Returned, No checklist, Done, In progress, Not started.

**API surface**: no new or changed endpoint.

| Endpoint | Method | Use | Change |
|---|---|---|---|
| `GET /vrms/repairs/:id` | GET | issues, steps, resolution fields, `categoryName`, knowledge entry with `safetyNotes` | none |
| `GET /vrms/repairs/audit-logs?ticketId=` | GET | Activity | first call with `limit: 5`, then today's paging at 50 |
| `GET /vrms/ai/tickets/:id/diagnoses/latest` | GET | the AI one line | none |
| `POST /vrms/repairs/:id/attachments` | POST | photo drop on a zone | optional multipart `group` (`BEFORE` or `AFTER`), AC-21 |
| `PATCH /vrms/repairs/:id/attachments/:attachmentId` | PATCH | thumbnail drag between groups | none (spec 0018's Move) |
| ticket attachments list (spec 0017) | GET | photo counts | none |

**Value sourcing**:

| Action | Value produced / displayed | Source |
|---|---|---|
| Closed row | issue text without prefix | `issue.description` with a leading `[...] ` removed (`stripSystem` in a new `lib/issueRow.ts`, matching `issueDescription` in backend `ticket-inputs.ts`) |
| Closed row | category | `issue.categoryName` |
| Closed row | "Known fix: {name}", status, Safety word | `issue.knowledgeEntry` (`name`, `status`, `safetyNotes` trimmed and not empty) from the ticket response |
| Closed row | progress {x} of {y} | `mergedSteps(issue, overrides)`: `issue.steps` with `checkedAt` plus `useTickOverrides` at list level |
| Closed row | state | derived (AC-3) from steps, `resolvedAt`, and `hasSavedResolution` in `lib/resolutionForm.ts` |

**Key invariants**:
- The issue state is never stored and never sent; one pure function (`issueState` in `lib/issueRow.ts`) decides it, used by the row, the summary line and the open rule.
- The refresh changes values on rows, never which rows are open.
- Nothing about permissions moves to the client: Edit steps, ticks, Edit issue, Remove issue, Change and Cancel keep their current `can` flags (`editChecklist`, `work`, `edit`, `administer`, and the ticket's cancel action).
- A step action never sits on the closed row; the closed row is for reading.
- No new colour tokens; the bar and words use `status-in-progress`, `success`, `highlight`, `warning` and `muted-foreground`.

**Security model**: unchanged except AC-21 and AC-22: an upload may name its photo group under the same add right, and Before protection no longer covers Before photos added after work started. The page shows what the ticket response already carries for the caller; costs and documents keep their `ticket.costs.view` gate, Activity keeps `audit.view`, AI keeps its module switch.

**Configuration required**: none.

## Consequences

**Positive**:
- A 10 issue ticket fits on one or two screens; the work in progress is open, the rest reads at a glance.
- The verifier signs off from closed rows without clicking.
- The page now follows its own design file (title, phone order, Cancel, no boxes per item).
- No backend change, so no migration risk and nothing for the other groups.

**Negative / tradeoffs**:
- Done steps can't be hidden; a long, mostly done checklist stays long while its row is open (rows fold, so this costs scrolling only inside one issue).
- A Before photo added after work started is not protected, so a mechanic can remove one they put there by mistake; it is marked so a verifier knows it does not show the state before work.
- The photo card now has two drag systems: native file drops from the computer and `@dnd-kit` for moving thumbnails, each with its own feedback.
- Dropping photos is no longer advertised at rest; people find it through the add tile's tooltip or by trying.
- Activity is one more click away, though its newest entry still shows.
- Return to mechanic is outlined again next to the primary; the two choices at verification read as a pair.
- One more tap to see a closed issue's steps.
- Without Expand all, reading every issue means opening each row; the verifier reads the closed rows instead, and the page remembers what was opened.
- A phone no longer has its own Take photo button; the one add tile reaches the camera through the system picker, which is one more tap on some phones.
- Typical parts and hours are only on the knowledge entry now; someone who used them as a quick parts list opens the entry.
- The "Done" state means all steps ticked, not that the mechanic says the issue is finished; an issue with no steps never shows Done.
- Per tab memory means a new tab or another device starts from the default rule.
- Verification stays per ticket; a per issue sign off (topic 3) would add an Approved state to the row later.
- The AI card stays per ticket even though it now sits next to the issues.

**Neutral**:
- Feature 11's deferred tests now wait for this build.
- The shadcn Accordion is a new UI component in `src/components/ui/`.
