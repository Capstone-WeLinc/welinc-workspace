## Summary

The whole WeLinc suite goes on Azure, paid from a $200 free account (a teammate's trial, signed up on Nov 19 the day staging was first applied), so the 30 days of credit last past the final defense on Dec 5. Every web app is a free Static Web App, every service runs on Azure Container Apps behind the one gateway, and each environment (staging and production) gets its own small PostgreSQL server. The trial allows only one Container Apps environment, so production's apps run in staging's, every name ending in `-staging` or `-prod`, kept apart by their own keys, data and logins. Everything lives on `welinc.app` (the addresses in contract 0001), mail goes out through Brevo, and production keeps every app warm so the defenses never wait on a cold start. VMMS and BMS deploy into the same setup with a workflow template you give them; production goes live on Nov 20, well before the mock defense on Nov 28, and nothing risky changes during a freeze before the defenses (its dates are not set yet, see Timeline).

## Requirements

**User stories**:
- As a developer, I want every pull request checked automatically so that a broken build is caught before it merges.
- As a developer of any WeLinc group, I want a merge to `development` to reach staging without manual steps so that each system can be tested together before the integration defense.
- As the team lead, I want production to change only when a person chooses so that a bad merge cannot reach the defense system.
- As a panel member, I want every screen to answer quickly on the first click so that the demo looks like a working product.
- As the team, we want the whole setup recreatable and the data copyable so that losing the subscription does not mean losing the system.

**Acceptance criteria** (the contract, each independently checkable):
- **AC-1**: Every pull request into `development` in web-vrms, web-portal, backend-vrms, auth and analytics-ai runs a CI workflow (install, lint without fixing, build, tests where the repo has them) and shows pass or fail on the PR.
- **AC-2**: CI fails the run when lint, the build or a test fails.
- **AC-3**: A push to `development` in web-vrms, web-portal, backend-vrms or auth deploys that repo to staging with no manual step. A push to `main` in the workspace repo that changes `infra/gateway/**` deploys the gateway to staging the same way. A VMMS or BMS repo that adds the template from `docs/integration/hosting.md` gets the same behavior for its own apps.
- **AC-4**: Production deploys only from a manual "Run workflow" run on the `main` branch of that repo. A push or merge to `development` never deploys production, and a push to `main` alone deploys no production (in the workspace it deploys the gateway to staging, AC-3). Nobody pushes to `main` by hand, apart from the one time fast forward to `development` in task 13 (a plain fast forward, never a force push, done before the first production run because a manual run reads the workflow file on `main`): a production run with no `sha` input promotes, moving `main` forward (fast forward only) to the newest `development` commit whose staging deploy succeeded, then deploys it. A run with a `sha` input is a rollback to an older `main` commit and moves nothing. The deployed commit must be reachable from both `main` and `development` (the workspace repo has only `main`, so only that, and it never promotes), and for a backend or the gateway its image must already exist in the registry (built by the staging deploy of that commit), otherwise the run fails. The VMMS and BMS template works the same way.
- **AC-5**: Staging and production are separate in everything but the Container Apps environment (AC-23): their own resource group, PostgreSQL server, databases, database roles and passwords, storage accounts, pull identity, signing keys (`AUTH_SIGNING_KEYS`), client keys, internal service keys (every group secret differs per environment), mail credentials, Gemini key, allowed origins and addresses. A staging service holds no production password or key, so it can't open the production server or pass a production service's checks. In production no service accepts a localhost origin, and every production URL setting refuses localhost at boot (spec 0010).
- **AC-6**: Database migrations run automatically before a backend revision takes traffic, after `npm run env:check` passes in the same job. If the check, a migration, or the new revision's startup or readiness probe fails, the deploy fails and the previous revision keeps serving. The deploy succeeds only once the revision named after its commit and run attempt is ready and holds 100% of traffic.
- **AC-7**: Every address any client or setting uses is HTTPS on `welinc.app`, exactly as contract 0001 section 1 lists them: `portal.`, `vrms.`, `vmms.`, `bms.` and `api.welinc.app` for production, and the same names with a `staging-` prefix for staging. Certificates are Azure managed and renew on their own. The default Azure hostnames stay reachable (Azure can't turn them off) but no setting, client row or document uses them.
- **AC-8**: Database backups are automatic on both servers with at least 14 days kept, and one restore of the production server into a scratch server has been tested before Nov 26.
- **AC-9**: After every deploy a smoke test checks `https://<api>/health`, `/auth/health`, `/vrms/health` (each confirming a database connection), and that the portal and VRMS web return their page. It runs only after AC-6's revision check, retries for up to 3 minutes, and any failure marks the deploy failed. The VMMS and BMS template does the same for their health route and web app.
- **AC-10**: Running the Bicep files against empty resource groups in any subscription recreates the whole system, minus data. The runbook lists the one time steps (resource providers, resource groups, budget, Entra app registrations, bringing `main` up to `development` once per repo, DNS records, Brevo domain records) and covers moving data with `pg_dump` and restore and copying blobs and the file share.
- **AC-11**: No long lived Azure password is stored in GitHub, and no secret value is committed to any repo. Deploys log in with OpenID Connect (a short lived pass). Each deploying repo family has its own app registration per environment: ours (shared services, VRMS, gateway), VMMS's and BMS's. One more login, `welinc-registry-purge`, trusts only the workspace's `main` and holds only Reader and `AcrDelete` on the registry, for the weekly image purge. A staging login trusts only `development` (`main` for the workspace), a production login only `main` (in the workspace both logins trust `main`, and only the manual production run uses the production one), and the VMMS and BMS logins can update and start only their own group's apps and jobs. The shared registry is the one exception: any group's push right covers every image in it (accepted, see Security model). Workflows default to `contents: read`.
- **AC-12**: A budget on the subscription emails you at $50, $100, $150 and $180 of spend. The runbook says how to stop staging (scale to zero and stop its PostgreSQL server) in one command.
- **AC-13**: The seed guards hold on Azure: welinc-auth's seed refuses production and runs on staging only with `SEED_ALLOW=staging` (spec 0006), and backend-vrms's seed gets the same guard. Staging is seeded once at first deploy by a manually started seed job, with the public test passwords from `docs/integration/seed-accounts.md`.
- **AC-14**: Files survive restarts: profile pictures uploaded to auth (Azure Files share at `/app/uploads`) and ticket files in VRMS (Blob Storage, `vrms-attachments` container, spec 0017) are still there after a restart, a new revision or a scale to zero.
- **AC-15**: Production starts with no seed people. The migration job runs `npm run db:deploy` (migrations plus `catalog:sync`). Then auth's seed job runs `npm run seed:clients` with the production `CLIENT_*` values, then `npm run admin:recover -- --create --email <you> --name "<your name>" --reason "<text>"` (suite spec 0013 AC-12b), which creates the first suite admin and mails the setup code (if the mail fails, the job exits 1 and the person uses Forgot password once mail works). VRMS production gets reference data only (`npm run seed -- --reference`: garages, vehicles, knowledge base, settings), never mechanics, drivers, tickets or knowledge suggestions. Every knowledge entry is credited to a fixed setup actor (name `WeLinc setup`, email `setup@welinc.app`, no user id, no role), dated at seed time with one `ENTRY_CREATED` history row. `setup@welinc.app` is only a label: it is never created as a mailbox, or its owner would appear to be the setup actor. `--reference` runs in any environment (no `SEED_ALLOW`); its only guard is that it refuses (exit 1, nothing written) when the database already holds any garage, vehicle or knowledge entry, whatever its status. The whole run is one transaction, so a failure leaves nothing behind and a rerun works. Everyone else is invited from the portal with a setup code.
- **AC-16**: Replicas follow one rule. Production: every app keeps at least 1 replica. Staging: the gateway and every app that runs work on a timer (welinc-auth, backend-vrms, and any VMMS or BMS service its group marks as timed) keep 1 replica; every other staging app scales to zero, and a first call to it may answer 504 while it wakes. welinc-auth is set to at most 1 replica (its sign in limits count in its own memory; during a deploy the old and new revision overlap for a moment, which is accepted). BMS's inner services (booking, dispatch, completion, projection, analytics) run at most 1. Every other app runs at most 2.
- **AC-17**: Mail works before anyone is invited: welinc-auth sends through Brevo SMTP from `noreply@welinc.app`, the domain carries Brevo's DKIM records, its domain code and a DMARC record (no SPF record: Brevo sends from its own return path), and a code sent on staging to a real Gmail inbox arrives in the inbox (not spam) within 2 minutes.
- **AC-18**: The real client address reaches the services: on staging, two sign ins from two different networks show two different addresses in `account_events`, with the gateway at `TRUST_EDGE_PROXY=1` and the services at `TRUST_PROXY_HOPS=2` (suite spec 0008 follow up).
- **AC-19**: The VMMS and BMS services run inside the same Container Apps environment on internal ingress, reachable only through the gateway's `/vmms/` and `/bms/` routes, each with its own databases on its environment's server (`vmms`, and `bms_booking`, `bms_dispatch`, `bms_completion`, `bms_analytics`). Until a group deploys, its routes answer 502 `UPSTREAM_UNAVAILABLE` and nothing else breaks.
- **AC-20**: A shutdown copy exists before the credit ends: on or after Dec 6 (after the final defense) and before the credit end date, every production database is dumped with `pg_dump`, the blob container and file share are copied, and the copies sit on your machine and one teammate's. The runbook step records the date it ran.
- **AC-21**: Each PostgreSQL server's connections stay inside its budget (the table in Design) at full scale plus one deploy overlap: every service caps its pool with `DB_POOL_MAX`, and the sum never exceeds 35.
- **AC-22**: Every deploy, staging and production, runs the repo's own CI (lint, build, tests, audit) on the commit it deploys, in the same workflow run, and deploys only when CI passes. A commit pushed straight to `development` with a failing check never reaches staging; the run fails before any Azure login. The VMMS and BMS template works the same way.
- **AC-23**: Both environments' apps and jobs run in one Container Apps environment without clashing: every app and job is named `<base name>-<env>` with `<env>` `staging` or `prod` (for example `auth-service-staging` and `auth-service-prod`, `vrms-migrate-staging` and `vrms-migrate-prod`), staging's in `rg-welinc-staging`, production's in `rg-welinc-prod`; no app or job with a bare base name exists. The environment level parts are named the same way (file storage `auth-uploads-staging` and `auth-uploads-prod`, gateway certificate `cert-api-staging` and `cert-api-prod`). Every internal address an environment uses (`*_UPSTREAM`, `AUTH_INTERNAL_URL`, `AUTH_JWKS_URL`, any group setting that names another app) points at an app with its own ending, never the other one. A staging deploy changes no production app, and a production deploy changes no staging app. The production deploy logins can place apps in the environment (`join`) but can't change or delete it.

## Decision

**Chosen option**: Option 1 kept and widened: Azure Static Web Apps, Container Apps and PostgreSQL Flexible Server, deployed by GitHub Actions and described in Bicep, now for the whole suite on `welinc.app`, with one PostgreSQL server per environment and a deploy template for VMMS and BMS.

Every web app (portal, VRMS, VMMS, BMS) runs on a Static Web App per environment (8 of the 10 the Free plan allows). Every service, the gateway included, runs on Container Apps from images in one Azure Container Registry, in one Container Apps environment that staging owns and production joins (the trial allows only one): production's apps and jobs sit in `rg-welinc-prod`, and every app and job name ends in `-staging` or `-prod`. Each environment has its own Burstable PostgreSQL server holding that environment's seven databases. Production is fully warm; staging is warm only for the gateway and where a timer must keep running. Each group deploys its own apps with its own scoped Azure login.

**Implementation skills**: `azure-container-apps` (`microsoftdocs/agent-skills`, `.claude/skills/azure-container-apps/`) · `azure-container-registry` (`microsoftdocs/agent-skills`, `.claude/skills/azure-container-registry/`) · `azure-static-web-apps` (`microsoftdocs/agent-skills`, `.claude/skills/azure-static-web-apps/`) · `azure-blob-storage` (`microsoftdocs/agent-skills`, `.claude/skills/azure-blob-storage/`) · `azure-deployment-preflight` (`github/awesome-copilot`, `.claude/skills/azure-deployment-preflight/`) · `docker-patterns` (`.claude/skills/docker-patterns/`, its examples use Node 22; we run 24). Never `azure-prepare` or `azure-deploy` (they assume azd).

**Network**: the gateway has public ingress with a custom domain. Every other app has internal ingress with `allowInsecure` off, so every internal call is HTTPS on port 443 and the ingress `targetPort` equals the app's `PORT` (gateway 3000, auth 3001, backend-vrms 3002, VMMS and BMS from contract 0001 section 2). Each PostgreSQL server allows Azure services only, SSL required. Work from a laptop (`init.sql`, dumps, the restore drill) goes through a temporary firewall rule for your address that `apply.sh` and the runbook commands add and remove. The blob account allows backend-vrms's identity only, and the browser gets signed links (spec 0017); its CORS rules allow the VRMS web origin for `GET`.

**Internal addresses**: `https://<app name>.internal.<environment default domain>`, where the domain is the Container Apps environment's `properties.defaultDomain`, a Bicep output. Both WeLinc environments share that domain, so the app name is the only thing that tells `auth-service-staging` from `auth-service-prod`: Bicep builds every name from one `nameSuffix` (`-staging` or `-prod`, from `envName`) and never writes a bare base name. Contract 0001's service names (section 2) stay the base names; the suffix is a hosting detail. Every `*_UPSTREAM`, `AUTH_INTERNAL_URL` and `AUTH_JWKS_URL` uses this form (nginx ignores search domains, and `AUTH_JWKS_URL` must be HTTPS because the startup check refuses anything else in production).

**Gateway on Azure**: the same image as local, with hosted settings: each `*_UPSTREAM` is the internal address above, `ALLOWED_ORIGINS` the four web origins of that environment, `TRUST_EDGE_PROXY=1`, `GATEWAY_HSTS=max-age=86400`, rate 20 and burst 40. An upstream that isn't deployed yet answers 502 on its own routes only.

**Cookies and the domain**: every web app and the gateway share `welinc.app`, so the refresh and SSO cookies are first party (contract 0001 section 7). Hosted, the cookies carry `Secure` and the `__Secure-` prefix (`SSO_COOKIE_SECURE=true` on auth, `SESSION_COOKIE_SECURE=true` on backend-vrms).

**Custom domains in two passes**: certificates can only be issued once the DNS records exist, so `apply.sh` runs twice per environment. Pass 1 (`bindDomains=false`) creates everything with default hostnames. `dns-records.sh` then prints, from the Bicep outputs, a CNAME per name (to its Static Web App or the gateway's default hostname), the `asuid.<name>` TXT record holding the environment's `customDomainVerificationId`, and any TXT record a Static Web App asks for. You add them at the registrar and wait until `dig` shows them. Pass 2 (`bindDomains=true`) adds the Static Web App custom domains (CNAME validation) and, for the gateway, binds the hostname with `bindingType: Disabled`, creates the managed certificate, then switches the binding to `SniEnabled`.

**Revisions and probes**: single revision mode. Each deploy sets `revisionSuffix` to `r<first 7 of the SHA>-<github.run_attempt>`: Container Apps wants a suffix that starts with a letter, and the attempt number keeps a rerun or a rollback to an earlier SHA from clashing with an existing revision name. A startup probe on the health route allows up to 240 seconds (failure threshold times period) for boot and migration warm up; a readiness probe on the same route follows. Neither is a liveness probe, so a database outage does not restart loop the apps. `/health` routes may add the commit SHA later; not required.

Server parameters on both: `idle_in_transaction_session_timeout=60000` (a transaction left open holds back the directory feed, suite spec 0005), and `azure.extensions` allows `VECTOR` (pgvector, spec 0013) and `PG_TRGM` (the VRMS baseline migration creates `pg_trgm`, so without it the first migration fails).

**Connection strings**: `postgresql://<role>:<password>@<server>.postgres.database.azure.com:5432/<db>?sslmode=require&uselibpqcompat=true`. The last flag keeps `sslmode=require` meaning "encrypted" in node postgres instead of full certificate checking. Role passwords are 32 random hex characters, so they never need escaping in a URL. Bicep builds every `DATABASE_URL` in this form from the role passwords in the private file; the private file never holds a full URL, so a password lives in one place only.

**Database roles** (`infra/db/init.sql`, run as the server admin once per database, before the first migration): create `<db>_owner` and `<db>_app`; make `<db>_owner` own the database and its `public` schema (PostgreSQL 16 lets only the owner create there); `ALTER DEFAULT PRIVILEGES FOR ROLE <db>_owner` granting `<db>_app` `SELECT, INSERT, UPDATE, DELETE` on tables and `USAGE, SELECT` on sequences, so tables made by later migrations are covered; on `vrms`, `CREATE EXTENSION IF NOT EXISTS` for `vector` and `pg_trgm` as the admin, and `vector` on `vmms` (VMMS analytics; added 2026-11-19). Azure checks the right to create an untrusted extension before it checks whether it exists, so a migration's own `CREATE EXTENSION IF NOT EXISTS vector` is still refused for the owner role: a migration guards it with `DO $$ BEGIN IF NOT EXISTS (SELECT 1 FROM pg_extension WHERE extname = 'vector') THEN CREATE EXTENSION vector; END IF; END $$;` (backend-vrms's `ai_diagnosis` does; VMMS analytics needs the same). `pg_trgm` is trusted, so its plain `IF NOT EXISTS` works. The Azure admin is no superuser, so `init.sql` first grants itself membership in `<db>_owner` (PostgreSQL 16 needs that to hand the database over and to set default privileges for the role). It revokes `CONNECT` and `TEMPORARY` on each database from `PUBLIC` and grants `CONNECT` to that database's app role, so one database's roles can't open another database on the same server. It grants only through default privileges, never on tables that already exist, so a rerun never undoes the `audit_logs` revoke. The append only rule on `audit_logs` (spec 0021) runs after migrations, because the table doesn't exist when `init.sql` runs: backend-vrms's migration job ends with `REVOKE UPDATE, DELETE, TRUNCATE ON audit_logs FROM vrms_app` (idempotent, safe on every deploy).

**Fresh databases, no history to move**: every hosted database starts empty and runs all migrations in order on first deploy. The spec 0013 AC-28 export before the drop of VRMS `permission_changes` only matters for a database that already holds rows, so it does not apply here. The permission matrix lives in welinc-auth from the first `catalog:sync`.

**CI (`ci.yml`, every repo)**: built (Slice 1), hardened 2026-11-16 (`npm audit --omit=dev --audit-level=high`, `actions/*@v7`, `dependabot.yml`, auth's database tests in a `db` job on PostgreSQL 16; the workspace checks Bicep, shellcheck and the gateway routes). Runs on `pull_request` into `development`, and on `push` to `development` only in repos with no `deploy.yml` yet (once a repo deploys, its deploy runs CI for pushes, so CI never runs twice in one concurrency group); the workspace runs it on `pull_request` and `push` for `main`.  Node from `.nvmrc` (24), `permissions: contents: read`, cancels older runs of the same PR, caches npm, times out at 15 minutes. It also declares `on: workflow_call` with an optional `ref` input (a full SHA, passed to `actions/checkout`), so a deploy can run it on exactly the commit it deploys. Its concurrency group includes `github.workflow` and the event name, so a called run never shares a group with a pull request run.

**Deploy guard (AC-22)**: the first job of every `deploy.yml` is `ci: uses: ./.github/workflows/ci.yml` with `ref` set to the commit being deployed, and the deploy job has `needs: ci`.

**Which environment**: the trigger decides, nothing else. A `push` to `development` (workspace: `main`) is staging. A `workflow_dispatch` is production, and its first step fails unless `github.ref` is `refs/heads/main`, so a run started from the default branch by mistake does nothing. No job uses `environment:` (it would change the OIDC subject). `id-token: write` is set on the deploy job only.

**Deploy order**: each `deploy.yml` sets `concurrency: deploy-${{ github.repository }}-<staging|production>` with `cancel-in-progress: false`, so deploys of one environment queue and never overlap a migration. A production run of a SHA should start only after staging's run of that SHA finished; the image check below enforces it.

**Promotion (one click)**: a production run with no `sha` input first picks its target: the head commit of the newest successful staging run of this same `deploy.yml` (`gh run list --workflow deploy.yml --branch development --event push --status success --limit 1 --json headSha`), so it can only promote what staging really deployed. A `promote` job (the only job with `contents: write`, plus `actions: read` to list runs) then runs `git push origin <target>:main` with the workflow's own token. That push is a plain fast forward: if `main` holds a commit `development` doesn't, it fails and nothing deploys. A push made with the workflow token starts no other workflow, so it can't trigger itself. Then the deploy guard runs CI on the target, and the deploy job deploys it. If `main` already equals the target, the push is a no op and the run redeploys the same commit.

**The `sha` input** (production only, optional, for a rollback): must match `^[0-9a-f]{40}$`, is passed to steps through `env:` and never pasted into a shell line, and must already be on `main`. With it set, the run skips the promote job.

The Azure login happens only in the deploy job, so a red check means no login and no change. GitHub Free can't block a direct push to `development`; the deploy guard makes such a push harmless instead.

**CD for a backend (`deploy.yml`)**: on push to `development` (staging) or `workflow_dispatch` on `main` (production, with an optional `sha` input for a rollback), after the deploy guard:
1. Log in with OIDC using that environment's app registration.
2. Staging: build `Dockerfile.prod` (the runner image) and its `seed` target, tag both with the commit SHA, push them. Production: check out with full history, resolve the commit (the `sha` input, else the target the promote job moved `main` to), check it is reachable from both `main` and `development` (`git merge-base --is-ancestor`), and that both `<app>:<sha>` and `<app>-seed:<sha>` exist (`az acr repository show -n <registry> --image <app>:<sha>`); fail if any is false.
3. Skip this step on a rollback (a production `sha` that isn't the `main` head): migrations only add, so older code runs on the newer schema, and an old migration job must not run against a newer database. Otherwise set the migration job's image to the `seed` image of that SHA and its command with `az containerapp job update --image <seed> --command npm --args run db:deploy:job`, start it with a plain `az containerapp job start` (no override: an override at start replaces the whole container, settings and secrets included), and poll `az containerapp job execution show` until it ends (`replicaTimeout` 600, `replicaRetryLimit` 0). `db:deploy:job` is `npm run env:check && npm run db:deploy` in both repos (auth: migrations plus `catalog:sync`; backend-vrms: migrations plus the `audit_logs` revoke), connected as the owner role. A failed migration leaves Prisma's P3009 on the next run: clear it with `npx prisma migrate resolve --rolled-back <migration>` run once by the job, then rerun the deploy. On failure, print the job's logs and stop.
4. Update the Container App to the runner image with `revisionSuffix` set to `r<sha7>-<run_attempt>` (Revisions and probes).
5. Poll until `latestReadyRevisionName` is the new revision and it holds 100% of traffic, up to 6 minutes; on timeout, fail (the old revision keeps serving).
6. Run the smoke test.
It never runs a down migration.

**CD for a frontend (`deploy.yml`)**: log in with OIDC, build with that environment's `VITE_*` values as build settings (a plain `npm run build` refuses missing or localhost values, spec 0010), read the Static Web App deployment token at run time with `az staticwebapp secrets list`, deploy with the Static Web Apps action, run the smoke test. Production first checks the commit (the `sha` input, else the `main` head) is reachable from both `main` and `development`, then checks it out and builds it with production's `VITE_*` values. A web app has no image, so production rebuilds from the same commit staging tested rather than reusing the same files.

**Gateway CD (workspace repo)**: staging on a push to `main` that changes `infra/gateway/**`; production by a manual run on `main`, deploying the `sha` input if given, else the newest `main` commit that touched `infra/gateway/` (`git log -1 --format=%H -- infra/gateway`), since only those commits have a gateway image; its image must exist; image tagged with the commit SHA; same revision wait as a backend.

**Seed and bootstrap jobs**: every job runs from the service's `seed` image, a full source image (it carries `src/`, `scripts/`, `prisma/`, `tsconfig.json` and `prisma.config.ts`, since `ts-node` needs them) with the same settings and secrets as its app. A job's command is set on the job with `az containerapp job update --command … --args …`, then the job starts with no override (an override at start replaces the whole container, so the job loses its settings and secrets). The Azure CLI reads any argument that starts with a dash (`-c`, `--rolled-back`, `--create`) as one of its own options, so a command is an npm script with plain words (`npm run seed`), or, when it needs dash arguments (`admin:recover -- --create …`, `migrate resolve --rolled-back …`), it is set through the REST API: `az rest --method patch` on the job with `properties.template` carrying the new `command` and `args`. - VRMS seed job (owner role, `vrms_owner`): staging `npm run seed` with `SEED_ALLOW=staging`; production `npm run seed -- --reference` (AC-15: the setup actor, empty database only, one transaction). `--reference` needs no `SEED_ALLOW`. The owner role, because the full staging seed switches the `audit_logs` triggers off for its reset (`ALTER TABLE … DISABLE TRIGGER`), which only the table owner may do, and the app role has no `DELETE` on that table. `--reference` writes no audit rows, but one job keeps one role.
- Then each group seeds its own copy of `people.json` on staging (S11 guides). No `SEED_ALLOW` on production, ever.

**Key invariants**:
- A migration that ships with a backend must work with the previous revision too (additive first), because a rollback never undoes the database. During the freeze only additive migrations ship.
- Staging deploys never touch production resources. No staging login has any right on `rg-welinc-prod`, and no group's login has rights outside its own apps (the shared registry aside). The one shared resource is the Container Apps environment in `rg-welinc-staging`: our staging login's Contributor covers it, so only `apply.sh` (run by you) ever changes its settings, never a workflow.
- No Bicep name and no setting is written without its environment's `nameSuffix`, and no name is over 32 characters (`check-names`).
- While production runs, `rg-welinc-staging` and `cae-welinc-staging` are never deleted (delete locks); stopping staging means scaling its apps to zero and stopping its PostgreSQL server. A lock on a resource also covers its child resources, so the `CanNotDelete` lock on `cae-welinc-staging` (named `keep-cae-welinc-staging`) blocks deleting any certificate or environment storage on it, staging's included: deleting one of those means lifting that lock, deleting, and running `apply.sh prod` again, which puts it back (`infra/README.md`, *Shared environment*).
- No seed people ever exist on production.
- welinc-auth is set to 1 replica; the only overlap is the few seconds of a revision change, when sign in limits reset and its sweepers may run twice (they are idempotent updates; task 5 confirms it).
- A service with a timer never scales to zero.
- The sum of pools on a server never exceeds 35.
- Rollback: rerun the production workflow with the `sha` input set to an older `main` commit; `main` itself never moves back and is never force pushed after the one time cleanup. Its image must still exist (the purge keeps the last 15 tags per image). No down migration runs.
- The private secrets files are in the workspace `.gitignore`, and a copy lives somewhere a teammate can reach (the runbook names where).

**Security model**: anyone with write access to a repo can move its `main` branch and run its production workflow; GitHub Free can't require a reviewer on private repos. What the setup enforces is separation: staging logins only from `development`, production logins only from `main`, every deploy only after CI passes, each group only on its own apps. The registry is shared and its push right covers every image, so a group could overwrite another group's tag; accepted for the defense window instead of a custom registry permission model, and reduced by deploying immutable SHA tags only. Each PostgreSQL firewall admits any Azure service, other customers' included, so every role password is long, random and unique. App roles can't alter tables, and VRMS's can't edit or delete its audit log. The one exception is the `vrms-seed` job, which holds `vrms_owner` (Seed and bootstrap jobs): only a person starting it by hand can touch `audit_logs`, and on production it only ever runs `--reference`, which refuses a database that holds data. Hosted cookies are `Secure`, `HttpOnly`, `SameSite=Lax`, host only, with the `__Secure-` prefix. **Shared environment (accepted risk, 2026-11-19):** staging and production apps sit in one Container Apps environment, so a staging app can reach a production app's internal address and the reverse (Azure keeps internal ingress to the environment, not to a resource group). What stops misuse is that every internal call is authenticated with that environment's own keys: welinc-auth checks client assertions against its own client keys and signs with its own `AUTH_SIGNING_KEYS`, VRMS checks tokens against its own environment's JWKS, and each group's internal keys (`BMS_INTERNAL_SERVICE_KEY` and the like) must differ per environment (AC-5). A health route stays open to both, which reveals nothing. Also accepted, each for the defense window: both environments' logs land in one workspace, and the group staging logins' Reader on `rg-welinc-staging` lets them query production's app logs too (request lines with emails and addresses; no secrets or codes, production logs no seed codes); our staging deploy login, which trusts `development`, holds Contributor on `rg-welinc-staging` and so could change the environment or create an app named `*-prod` there, but every staging workflow only updates its own named app and job, the delete locks stop it removing what production needs, and only `apply.sh` (run by you) changes the environment; a change to the environment affects production too. Compliance scope: staff names, emails and phone numbers; no payments or health data. HTTPS, the firewalled servers, Container Apps secrets, managed identity for blobs and the account activity log (spec 0011) are the controls.

## Migration plan

**Strategy**: no live migration. Nothing is hosted today; every hosted database starts empty.
**Phases**:
1. Staging first (Slices 3 and 4), then the other groups onto it (Slice 5), then production (Slice 6).
2. Production is new, so there is no cutover from an old host.
**Rollback**: per deploy, rerun the production workflow with an older `main` commit as `sha`. For the setup itself, the Bicep can be applied again or into another subscription.
**Risks**: DNS records or certificate checks taking hours (add the records the day staging is applied); Brevo domain approval delays (start in task 12); a group's move landing late (their routes answer 502 and nothing else breaks; on 2026-11-14 neither VMMS nor BMS could deploy yet, see rationale.md); a trial subscription's low quota in the chosen region (checked in task 13).

## Consequences

**Positive**:
- The whole suite runs on one address, so the integration defense shows three systems behind one login.
- Every merge reaches staging by itself, for every group, and production changes only when someone chooses.
- Production never waits on a cold start, and the timers keep running everywhere.
- Staging and production can't touch each other's data.
- The setup is code and the data can be copied, so a lost subscription is a few hours of work, not a lost system.

**Negative / tradeoffs**:
- The credit is a hard end date, not just an amount. After about Dec 17 the subscription stops unless someone upgrades it with a card; the system goes offline after the defenses by design.
- Production approval is only a person clicking "Run workflow". GitHub Free can't enforce a second reviewer or required checks; the deploy guard (AC-22) makes sure CI at least passed.
- You become the operator for three groups: their app registrations, roles, secrets and client keys go through you, and their deploy problems land in your inbox.
- Any group can overwrite another group's image tag in the shared registry.
- Staging and production share one Container Apps environment (the trial's limit): their apps can reach each other's internal addresses (only keys keep them apart), their logs mix in one workspace, an environment wide outage or a bad environment setting hits both, and staging had to be recreated once under the new names (about an hour, staging down for part of it). Separate environments are the normal practice; this is the fallback the subscription forces.
- Every pool is small (2 or 3); a slow query holds a scarce connection, and a group that ignores the pool setting can starve the others.
- Estimated spend is $75 to $125 for the month the credit lasts, under the $200 (unconfirmed until task 13's pricing check), which leaves little room for mistakes like a noisy log or a forgotten scratch server.
- GitHub's 2,000 free minutes are shared by every group's builds; a busy week of Docker builds can use them up.
- Frontends are rebuilt per environment, so staging and production don't run the same build.
- A cold staging app answers 504 on its first call while it wakes.
- The domain's free year ends; renewal is a paid step if the suite outlives the course.

**Neutral**:
- The local docker compose files stay as they are for development.
- Mobile apps (the VMMS Expo app) point at `https://api.welinc.app`; building and sharing the app stays with VMMS.
- The default Azure hostnames stay reachable but unused.
- backend-vrms carries a copy of the auth controller the gateway hides; harmless and unreachable.
